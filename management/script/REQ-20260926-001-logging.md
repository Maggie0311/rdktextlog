## 1. 需求原文要点（来自用户，未改写）

1. 基于 RDK X5 开发适用于 RoboMaster 比赛的**文本日志系统**；
2. **赛场上自动记录**信息；发生错误时**自动记录**；
3. 错误以**错误码分类**：初始化不成功 / 通信问题 / 硬件问题 / 状态机没能正常流转等；
4. 输出格式符合业内较好的日志标准：**时间戳、错误码、优先级（级别）**等字段；
5. **场下直接看日志快速定位问题**，替代传统的依赖 Keil 在线调试的工作方式；
6. 充分利用 RDK X5（Linux 平台）**自带日志系统**可直接使用的部分，在其上开发适配比赛场景的文本日志；
7. 本轮先做**初步开发**：验收效果 = 一个**可运行的初步文本日志平台** + **场下使用方法**；
8. 开发思路要求**分阶段、分模块，清晰详细**（本文 §4 / §5）。

## 2. 团队路线中的定位（依据 `from_human/开发节奏规划.docx`）

- 本需求属于**阶段一「基础平台搭建和验证」**的软件目标："实现基础的文本日志系统"；同阶段还要求基础数值日志、波形查看、AI 闭环工作流、1kHz 节拍线程与进程自启动等；
- **阶段三「中央RT闭环方案推广」**的软件目标升级为："实现**稳定**的文本日志系统"——即阶段一交付允许"可用、可验证"，阶段三要求"稳定、高性能"；
- 规划明确阶段一追求"**维测效率相较纯 MCU 方案体现出优势**"、"初步接触以日志而非断点为主的调试方式"——文本日志是本团队新工作方式的**第一块基石**，其"场上自动记、场下快速查"的体验直接决定后续推广接受度。

## 3. 平台分析：RDK X5（Linux）自带日志设施盘点

> 结论口径：【直接用】= 开箱即用、比赛场景直接受益；【包装用】= 保留其能力，按比赛场景做封装/策略；【自建】= 平台没有、必须开发。逐项的板端核实动作已写入 T-001 的 AC8（不得凭假设宣称）。

| 设施 | 是什么 | 裁定 | 理由与比赛场景用法 |
|---|---|---|---|
| systemd-journald | 结构化系统日志内核，二进制存储，`journalctl` 查询，自带持久化配置（Storage=persistent 需核实开启） | 【包装用】 | 承接**系统级/进程级**证据面：服务崩溃、OOM、启动失败、内核报错。比赛日 `journalctl -b -1 -p err` 一条命令回看上次上电的所有错误。我们不自建"系统日志"，只做"比赛视角"的导出/快照脚本 |
| rsyslog / `/var/log/syslog` | 传统文本 syslog（系统镜像随 Ubuntu 提供，具体形态板端核实） | 【包装用】 | journald 的文本侧出口，便于 U 盘拷走即读；作为日志快照脚本的采集源之一 |
| dmesg / 内核 ring buffer | 内核态消息（驱动报错、SPI/I2C/CAN 异常、Oops） | 【直接用】 | **MCU 时代没有的东西**：总线级异常在 Linux 下有内核日志。`dmesg --time-format iso` 时间戳可与业务日志对齐。快照脚本必采 |
| systemd-coredump / core dump | 进程崩溃现场（核转储） | 【直接用+配置】 | 替代 MCU"跑飞只能干瞪眼"：进程段错误可留全现场。需板端核实/启用 coredumpctl，写入 T-001 核查项 |
| logrotate | 日志轮转守护 | 【包装用】 | 对我们业务日志与系统快照做容量治理；SD 卡写入策略由 developer 评估 |
| hobot_log（_sunrise log 库） | 地瓜 BPU/多媒体组件的日志库 | 【不依赖】 | 面向平台组件，非业务日志骨架；仅在对接 TROS 组件时由其自行落 journald |
| TROS 日志（ROS2 rcutils） | 机器人中间件日志 | 【不依赖，兼容】 | 本阶段不绑 ROS；P2 若引入 TROS 组件，用桥接器把其输出收编为事件即可 |

**必须自建的核心（平台没有的部分）**：面向**比赛业务语义**的一层——统一**错误码体系**（初始化/通信/硬件/状态机/系统）、**双时间戳**（墙上时钟 + 单调时钟，防 NTP 跳变与断电乱序）、**低开销高可靠写入**（控制线程到落盘的路径短、崩溃/断电时损失有界、进程崩溃前最后一条日志可达）、**人读行格式 + 机读解析工具**、**场上快照/黑匣子**策略、**与 journald/dmesg 的关联**。

**裁定总述**：采用"**平台层（journald/dmesg/coredump）直接用 + 业务层自建**"的分层方案。业务层命名为 **rmlog**（含 C 与 Python 双端同构接口），阶段一只依赖 Python 3 标准库与 POSIX，不引入第三方依赖（板端 pip/外网不可假设可用）。

## 4. 分阶段开发思路

### 阶段 P0（本轮，task：T-20260926-001-logging-platform-p0）——"可运行的初步平台 + 场下使用方法"

目标：业务日志层 rmlog 闭环——**记得到、落得下、查得出**。

- **P0-a 错误码体系**：错误码分域编号（INIT 初始化 / COMM 通信 / HW 硬件 / FSM 状态机 / SYS 系统资源），形如 `E-INIT-001`；每码绑定默认级别（INFO/WARN/ERROR/FATAL）、中文含义、建议动作；错误码表 C/Python 双端**同源**（单一表格生成/引用，避免两处漂移）。
- **P0-b 行格式 v1（人读 + 机读一致）**：一行一条，字段固定序：`<seq>|<墙上时间戳 ISO8601>|<单调时间戳 ms>|<LEVEL>|<CODE>|<MODULE>|<message>|<k=v 属性…>`；前缀标记 `LOGV1` 便于工具识别与残行丢弃；文本人读友好，同时可被读端解析。
- **P0-c 双端接口**：C 侧宏族（`RMLOG_I/W/E/F(mod, code, fmt, ...)`，线程安全、格式化失败不崩溃）；Python 侧 `rmlog.event(...)`；同一事件双端产生**一致格式**的行（自测验证）。
- **P0-d 可靠落盘**：单文件追加 + 行完整性保障（多进程并发写不产生交错半行）；按大小轮转保留 N 份；**崩溃/断电取证**：关键事件先落盘再返回（写入路径短、可控 flush），异常终止时已写内容可读，半行由读端按前缀标记丢弃。
- **P0-e 读端工具**：`rmlog_read.py`——`parse / tail / filter --level --code --since --until`；比赛日"一条命令定位某类错误"。
- **P0-f 证据与文档**：X5 实机运行证据（或按 Q1 裁决降级）；`USAGE.md` 场下使用方法（部署→开机自启→提取→快速定位）；与 journald/dmesg 的关联查法（同一时间戳区间比对）。

P0 验收效果（对应用户原话）："搭建一个可运行的初步文本日志平台，并给出场下使用方法"。

### 阶段 P1——"比赛可用"（阶段一收口，衔接团队规划验收）

- 进程自启动（systemd unit）+ 崩溃自动重启（Restart=on-failure），错误事件自动落盘无需人工；
- **场上黑匣子**：看门狗式轻量健康事件（节拍线程心跳、SPI 通信错误率、电压/温度越限），异常窗口自动提高记录密度；
- **日志快照包**：一键打包（rmlog 业务日志 + journalctl 导出 + dmesg + coredump 摘要 + 版本信息）到 U 盘/网络；赛后一条命令交打包件给 AI/队友分析；
- 与 1kHz 节拍线程、SPI 主从通信模块（团队规划的其他阶段一目标）对接：通信失败、控制超时自动产生 COMM/HW 错误事件；
- AI 闭环工作流对接：宿主机 agent 可经 WiFi 拉取日志快照并分析（团队规划阶段一目标之一）。

### 阶段 P2——"稳定高性能"（对应团队规划阶段三目标）

- 写入路径优化（批量化/低锁开销）、存储容量治理与寿命友好策略、长时间实车运行稳定性验证（按团队规划进入装车试点）；
- 与数值日志系统/波形查看方案（团队规划的另两个阶段一/三目标）共用错误码与时间基准；
- SPI 从机日志回传（规划中的专项：从机利用 SPI 富余带宽回传日志，统一收编进 rmlog 错误码体系）；
- 自动化测试与 CI（规划阶段三目标），错误码表变更走版本化。

## 6. T-001 验收标准（AC，冻结）

- **AC1 组件可运行**：`developer/script/rmlog/` 交付纯 Python3 标准库实现的日志组件与示例；内置自测 `python3 -m rmlog.selftest` 全部通过（开发机 Windows 与 X5 交叉目标环境均可跑或给出替代证据，见 AC8）。
- **AC2 行格式 v1**：样例日志行可被读端逐行解析；字段含 序号 / 墙上时间戳 / 单调时间戳 / 级别 / 错误码 / 模块 / 消息 / k=v 属性；残行（崩溃截断）被安全丢弃不污染解析。README 附样例输出。
- **AC3 错误码体系**：`ERR-CATALOG.md` 覆盖 INIT/COMM/HW/FSM/SYS 五域（用户四类错误 + 系统资源类），每码含编号/默认级别/含义/建议动作；C 与 Python 常量同源。
- **AC4 双端一致**：同一事件经 C 宏与 Python API 产出格式一致的行（自测含双端对照用例）。
- **AC5 落盘与查询**：多进程并发写演示无丢行/无半行交错；超过大小上限产生轮转；`rmlog_read.py` 能按 `--level ERROR --code E-INIT-*` 一条命令过滤出目标行。
- **AC6 崩溃取证**：示例程序演示"硬错误前最后一条事件已落盘"；文档说明断电/崩溃后残行处理与预期损失边界。
- **AC7 场下使用方法**：`USAGE.md` 含：交叉编译与部署到 X5 的步骤、开机自启（systemd unit 样例）、WiFi 下日志提取方法、快速定位示例（"一次假想的场上故障如何 5 分钟内定位"）、本阶段局限与 P1 展望。
- **AC8 平台核查证据**：IMPL 中附对 §3 表格中【包装用/直接用】项的板端核实结果（journald 持久化状态、rsyslog 形态、coredump 可用性、dmesg 时间戳格式、Python3 版本、持久分区路径）；**若板端本轮不可达，按 Q1 裁决执行**，并在 IMPL 明确标注"未核实项"。
