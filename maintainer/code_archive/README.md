## 0. 醒目声明（文档统一入口）

> **所有「给人看的文档」统一在 `maintainer/` 下；`developer/script/` 里的是开发过程的原始产物（源码 + 实现说明 `IMPL` + 代码风格 `CODE-STYLE`），最终以 `maintainer` 归档版为准。**

- 想**用起来**、想**知道 v2 比 v1 多了什么**、想**理解它是什么/为什么这样写** → 读本目录的导航表（§1）指向的文档；
- `developer/script/` 里同名文档（`USAGE.md`、`IMPL-*.md` 等）是**开发过程的工作稿**，可能与归档版存在时点差；
  引用代码位置、判断"这一版到底什么样"时，一律回到 `maintainer/code_archive/` 归档件。

## 1. 读者 → 文档映射（按"你是谁 / 想干什么 → 按顺序读什么"）

> 路径均为**仓库根相对路径**。`…` 表示该 task 目录下的同名文件。

| 你是谁 / 想干什么 | 读什么（按顺序） |
|---|---|
| **电控队员，想上手用** | `developer/script/USAGE.md`（使用手册）→ `maintainer/code_archive/变更说明-v2.md`（v2 新功能 / 用法差异） |
| **想知道 v2 相比 v1 新增了什么、用法有何不同** | `maintainer/code_archive/变更说明-v2.md`（本任务核心，v1→v2 完整差异，逐条带 `file:line` 依据） |
| **想理解它是什么、开发过程、为什么这样** | `maintainer/code_archive/T-20260930-005-logging-v2/SPEC-001.md`（说明书·总览）→ `…/WALKTHROUGH-001.md`（逐模块走读）→ `…/DIFF-001.md`（版本差异） |
| **想改代码 / 接入开发** | `developer/script/rmlog/USAGE.md`（v2 API 要点）→ `maintainer/code_archive/T-20260930-005-logging-v2/WALKTHROUGH-001.md` → `developer/script/IMPL-T-20260930-005-logging-v2.md`（实现说明） |
| **想查某个名词/缩写是什么意思** | `maintainer/script/GLOSSARY.md`（项目级术语表，跨版本累积） |
| **想审计版本链 / 追溯"这一版怎么来的、谁验收的"** | `maintainer/code_archive/INDEX.md`（总索引）→ 对应 task 的 `VERSION-<NNN>.md`（版本卡） |

### 1.1 命名术语表（让文件名自解释）

| 命名 | 是什么 | 给谁看 |
|---|---|---|
| `SPEC-<NNN>` | **说明书**：给人类看的总览与开发过程（11 个冻结字段） | 人类用户（首要）、management |
| `WALKTHROUGH-<NNN>` | **逐模块代码走读**：教学向（模块→职责→关键函数→数据流） | 人类用户 |
| `DIFF-<NNN>` | **版本差异**：同一 task 内「上一归档版本 → 本版本」的差异（首版写「首版」） | 人类用户 |
| `QUESTIONS-<NNN>` | **关键问题清单**：读这份代码前应当先弄懂的 N 个问题 | 人类用户 |
| `USAGE.md` | **使用手册**（用户向）：怎么打、怎么查、怎么部署 | 电控队员 |
| `IMPL-*.md` | **实现说明**（开发者向）：关键决策、为什么这样写、已知风险 | 开发者 |
| `PLAN-*.md` | **开发计划**（开发者向）：差距分析、实施顺序 | 开发者 |
| `VERSION-<NNN>` | **归档版本卡**（审计向）：三份要件、双指纹、diff 结论、验收状态 | 人类用户、审计 |
| `变更说明-v2.md` | **跨 task 的版本差异**（v1→v2 完整对比）：v2 新增了什么、用法有何不同 | 电控队员 |

> **「版本差异」有两条线，别混**：`DIFF-<NNN>.md` 是**同一 task 内**相邻归档版本之间的差异；
> `变更说明-v2.md` 是**跨 task**（`T-20260926-001`(v1) → `T-20260930-005`(v2)）的完整差异。
> 本框架的「DIFF」概念落在后者（v1→v2）；原 v2 归档的 `DIFF-001.md` 按新任务写成「首版」、不含 v1→v2 对比，**以 `变更说明-v2.md` 为准**（详见该文件文末注记）。

## 3. 归档规则（摘要；完整约束见 `../role-limit/ROLE-LIMIT.md` §4）

### 3.1 与 `mailbox/archive/` 的区别（**必须区分**，委托层明确要求）

| | `code_archive/`（本目录） | `mailbox/archive/` |
|---|---|---|
| 归档什么 | **代码产物**（原件、带注副本、说明书、版本卡） | **邮件**（通信记录） |
| 组织维度 | **`task_id` + 版本号** | **`YYYY-MM`**（时间） |
| 检索问题 | "这个任务的第 3 版长什么样、为什么这么写" | "上个月谁跟谁说了什么" |
| 可否修改 | 原件**写入即冻结**；新增只能加版本 | 只读（邮件发出即冻结） |

**两处永不互相存放**：邮件留在邮箱；代码留在本目录。若某封邮件对归档有决定性作用（例如两方确认通知），
在**版本卡里引用其 `mail_id`**，而不是把邮件复制进来。

### 3.2 归档前置条件（**硬性，三份要件缺一不可**）

1. **`accepted` 验收结论**（附理由）← `management`（归档许可）；
2. **合格确认通知** ← `developer`（产物路径 / commit hash / 构建方式 / 自测证据 / 审查报告）；
3. **合格确认通知** ← `software_tester`（测试角度 / 报告路径 / **未覆盖项**）。

三者的 **commit hash 必须一致**；三份 `mail_id` 抄入版本卡；缺任一份不得归档；`rejected` 版本进 `_tombstones/`。

### 3.3 补注、冻结与双指纹

- **就地补注**：从来源逐字节复制到 `code/` 后，注释直接加在文件上（不另存第二份）；**只增以注释符号开头的行**，不改任何代码行（KN3）。
- **冻结**：补注完成即 `code/` 一字不改；要变只能新版本。
- **双指纹**（记入版本卡）：补注前 = 来源 commit hash + 逐文件 SHA-256；补注后 = `code/` 逐文件 SHA-256；外加 diff 结论（只含新增注释行）。
- **归档件不是审查/测试对象**：审查/测试一律以来源 commit 为准；引用代码位置须同时给出来源 commit 与归档版本号。

### 3.4 大文件策略 / 墓碑

- 二进制、打包件、构建中间物**不入库**：只记校验值 + 来源路径 + 重建方式。
- 未采用/被否决版本进 `_tombstones/`（版本、原因、依据），**墓碑不删**。

## 4. 目录结构（冻结）

```
code_archive/
├── README.md                本文件：文档导航入口 + 归档规则
├── INDEX.md                 总索引：task_id / 版本 / commit / 验收状态 / 三份来源 mail_id / 配套文档
├── 变更说明-v2.md           v1→v2 完整差异（新增功能表 + 用法差异 + 迁移注意点）
├── <task_id>/
│   ├── VERSION-<NNN>.md     版本记录卡（三份要件、双指纹、diff 结论、状态）
│   ├── SPEC-<NNN>.md        说明书（简洁总览；11 个冻结字段）
│   ├── WALKTHROUGH-<NNN>.md 逐模块代码走读（教学向）
│   ├── QUESTIONS-<NNN>.md   关键问题清单（读码前自查）
│   ├── DIFF-<NNN>.md        与上一版差异（首版写「首版」）
│   └── code/                **带注代码**：从来源逐字节复制后就地补注；补注完成即冻结
└── _tombstones/             未采用 / 被验收驳回 / 被否决版本的墓碑记录（**不删**）
```

（另：项目级**术语表**在 `../script/GLOSSARY.md`，跨版本累积。）
