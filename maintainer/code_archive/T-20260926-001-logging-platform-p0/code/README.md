# script/ — developer 的产物区（含交付代码）

> 本目录是本角色的**交付产物区**，也是本角色唯一的写区。
> **本框架不存在公共工作空间**：交付产物一律落在**生产者自己的 `script/`** 下——
> `developer` 的代码就在这里。（原始裁定见 framework_admin 的 `DECISION-20260924-005`，**仅供溯源**。）

## 1. 目录结构（**必须由本角色在本文件中声明**）

| 路径 | 内容 | 说明 |
|---|---|---|
| `script/<子目录>/...` | **源代码** | C / Python 为主；具体结构由本角色决定，但必须写在本文件中，否则消费方无法定位 |
| `script/tests/` | 测试代码（**默认位置**） | 若在 `CODE-STYLE.md` 中另行声明，以声明为准 |
| `script/dist/` | **交付包**（打包件） | 命名 `<task_id>.<ext>`；是否纳入 git 由本角色决定，但**必须可重建** |
| `script/CODE-STYLE.md` | 代码风格与注释规范 | management 用作验收依据之一；变更须先发 NOTIFY（接口冻结） |
| `script/IMPL-<task_id>.md` | 实现说明 | 改动清单 / 关键决策与理由 / 验证方式与输出 / 已知风险与未覆盖项 |
| `script/INDEX.md` | 产物登记表 | 登记**交付单元**（按 `task_id`），**不逐文件登记源码** |

## 2. 交付方式（跨角色流转，已冻结）

每次交付必须让消费方能够**独立复现**。发 `RESULT` 时必须在邮件中给出四项：

1. **路径** —— 交付物在本目录下的位置；
2. **commit hash** —— 审查（`code_reviewer`）与验收（`management`）均以此为准；代码一变，审查报告与验收结论即失效；
3. **可复现命令** —— 构建 / 运行 / 测试命令 + 输出摘要；
4. **打包件（可选）** —— 若打包，路径写入邮件的 `attachments` 字段。

**跨角色推进一律经邮箱**。需要改动他方产物时，发 `ISSUE`/`TASK` 给其所有者，**不得直接改**。

## 3. 权限

| 角色 | 对本目录的权限 |
|---|---|
| `developer`（本角色） | **读写（唯一写入者）** |
| `code_reviewer` | **只读**（审查依据） |
| `management` | **只读**（验收依据） |
| 其他角色 | **只读** |

## 4. 规范

- 命名 `<slug>.<ext>`；重大变更另存 `-v2`，**不覆盖历史**；
- 每个**交付单元**（一个 `task_id` 的产出批次、说明文档、打包件）必须登记到 `INDEX.md`；
- 交付前必须自测并在 `IMPL` 中留下可复现证据（`ROLE-LIMIT.md` §6 DoD）。
