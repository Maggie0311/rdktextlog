# SEVERITY — 严重级别定义与判定门槛（v1.0）

> 目的：让"要求他人返工"这件事**必须有凭据**。级别虚高一次，此后所有级别的可信度都会下降。

## 1. 级别定义

| 级别 | 名称 | 定义 | 是否阻断验收 |
|---|---|---|---|
| **BLOCKER** | 阻断 | 会导致功能错误、崩溃、数据损坏、安全漏洞、不可接受的资源泄漏，或**直接不满足 AC 的关键项** | **是**（不修不得验收） |
| **MAJOR** | 严重 | 在特定但现实的条件下出错；错误处理缺失导致故障难以定位；破坏既有接口或调用方 | **是** |
| **MINOR** | 一般 | 不影响当前正确性，但影响健壮性 / 可维护性，**且有条款依据** | 否（结论可为 CONDITIONAL） |
| **NIT** | 提示 | 风格与偏好类，有条款依据但价值低 | 否 |
| **INFO** | 范围外提示 | 本次交付范围之外观察到的问题 | 否（**绝不可阻断**） |
| **unverified** | 未确定 | 证据不足以判定成立与否 | 否（交由 management 决定是否投入） |

## 2. 判定门槛（硬性，不得突破）

| 若…… | 则级别不得高于 |
|---|---|
| **给不出可复现场景**（输入/状态 X → 后果 Y） | **MINOR**（禁止标 BLOCKER / MAJOR） |
| **找不到条款依据**（`CODE-STYLE.md` / 用户标准 / 本清单 / 根规范） | **NIT**（禁止要求返工） |
| 问题落在**本次交付范围之外** | **INFO**（禁止阻断，禁止要求本轮返工） |
| 无法确认是否成立 | **unverified**（禁止写成结论） |

> 反过来也成立：**能给出"输入 X → 崩溃 / 数据损坏 / 功能错误"的场景，就不得降级为 MINOR**。
> 门槛是双向的——它既防虚高，也防"和稀泥式降级"。

## 3. 判级的三个问题（按顺序问）

1. **会不会错？** 有没有具体的输入或状态让它产生错误结果？（没有 → 最高 MINOR）
2. **错到什么程度？** 崩溃 / 数据损坏 / 安全 / 静默错误 > 报错但可恢复 > 只是不好看。
3. **有没有条款？** 有 → 按 1、2 定级；没有 → 最高 NIT。

## 4. 反例：什么**不算**问题（防止制造不存在的错误）

| 情形 | 判定 | 理由 |
|---|---|---|
| "我更喜欢另一种写法" | 不写，或 NIT | 个人偏好不是标准 |
| "这里可以优化性能"（无实测数据） | 不写，或 INFO | 无证据的优化建议不是缺陷 |
| "应该加单元测试"（AC 未要求且用户标准未要求） | NIT | 有条款依据才可要求；测试范围属 management 决定 |
| "这段既有代码写得很烂"（非本次改动） | INFO | 范围外；改为让 management 决定是否建新 task_id |
| "变量名不够优雅"（符合 CODE-STYLE） | 不写 | 符合既定风格即为合格 |
| "如果以后需求变了这里要改" | 不写 | 对未来需求的猜测不是当前缺陷 |

## 5. 数量控制

- **同一根因的重复问题合并为一条发现项**，在"位置"字段列出**全部**出现位置。
  理由：把 1 个问题拆成 12 条只是让报告显得更长，对修复毫无帮助。
- 一个交付的发现项中若 NIT 占比过高，审查者应自问：**我是在检查代码，还是在展示认真？**
