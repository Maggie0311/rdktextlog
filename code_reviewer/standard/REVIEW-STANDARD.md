# REVIEW-STANDARD — 审查总纲（v1.0）

> 所有者: `code_reviewer` (R-004) · 依据: 本角色 `role-limit/ROLE-LIMIT.md`（§0 权力轴、§2.1 审查门）· 溯源: framework_admin 的 `DECISION-20260923-004`

## 1. 审查流程（7 步，不得跳步）

| # | 步骤 | 产出 |
|---|---|---|
| 1 | **固定被审对象**：记录 `task_id` 与 **commit hash**，列出被审文件清单 | 报告 §1 |
| 2 | **读取依据**：AC / 需求拆解书 / `CODE-STYLE.md` / `IMPL-*.md` / **`standard/user/` 全部用户标准** | 报告的"应用标准清单" |
| 3 | **建立覆盖声明**：逐文件标注"全查 / 抽样（比例与依据）/ 不查（原因）" | 报告 §2 |
| 4 | **逐项过清单**：`CHECKLIST-COMMON` + 对应语言清单 + 用户标准 | 发现项草稿 |
| 5 | **实际验证**（PASS 的必要条件之一）：至少做一项——编译/运行、静态检查、最小复现、逐分支推演 | 验证证据 |
| 6 | **定级与收敛**：按 `SEVERITY.md` 定级；无法判定的标 `unverified`；重复问题合并为一条（列全部位置） | 报告 §4–§5 |
| 7 | **出结论并发送**：按门槛给 PASS / CONDITIONAL / FAIL，发 RESULT（主送 developer，抄送 management） | 报告 §6 + 邮件 |

## 2. 结论定义与门槛

| 结论 | 成立条件 |
|---|---|
| **PASS** | 覆盖声明完整 **且** ≥1 项实际验证动作的证据 **且** 阻断级 / 严重级问题为 0 |
| **CONDITIONAL** | 仅存在一般级 / 提示级问题，逐条列出后续可处理项 |
| **FAIL** | 存在未解决的阻断级或严重级问题 |

> **PASS 是三者中最难拿到的结论。** 拿不到覆盖声明或验证证据时，正确做法不是"给个 PASS 算了"，而是**补齐后再出结论**。

## 3. 时效与不成为瓶颈

- 收到审查请求后 **≤1 轮**内出**首份结论**（可分批：先出覆盖声明 + 已达成的发现，再补细节，但不得延迟结论）。
- 一次审查的范围 = **一个 `task_id` 的交付**。范围过大时，发 QUERY 请 management 拆分。
- 复审（r2、r3）：**只审增量**（变更部分 + 原发现项 + 受影响路径），不重复全量走查，但**必须重新出结论并记录新的 commit hash**。

## 4. 与 developer 的交互规则（申诉通道）

1. developer 对任一发现项有异议 → 发 `ISSUE`（附证据）。
2. code_reviewer **≤1 轮**内以证据裁定：
   - 申诉成立 → **撤回或降级**该发现项，记入 `REVIEW-STATS.md`（这是可接受的、正常的修正，不是丢脸）；
   - 申诉不成立 → 补充**可复现证据**后驳回，不得仅凭"我认为"维持原判。
3. 发现项**五要素不全**者，developer 可**直接引用本条拒绝**，无需另行举证。
4. 证据冲突且无法收敛 → 标 `unverified`，交 management 决定是否投入；影响成败则升级人类用户。

## 5. 接口（谁依赖本标准的什么）

| 角色 | 依赖内容 |
|---|---|
| `developer` | 清单条目编号（用作自查与整改依据）、`SEVERITY.md` 门槛 |
| `management` | 审查结论（作为其验收前置；其自身一侧的规则写在其契约内） |
| 人类用户 | `user/` 接口（写入即生效） |
| `framework_admin` | 标准变更须发 NOTIFY；标准缺陷可发 ISSUE 修订 |

## 6. 明确不属于本标准的范围

- **不判断需求本身是否合理**（那是 management 与人类用户的事）。
- **不判断任务优先级、不决定是否返工**（management）。
- **不提供修复代码**（developer）。报告中的"建议"是方向性描述，不是实现。
