# user/ — ★ 人类用户自定义标准接口

> **本目录是给人类用户用的**。你在这里写下的检查要求，`code_reviewer` **每次审查都必须执行**。
> 本目录对 `code_reviewer` 是**只读**的——它不得删除、修改或弱化你写入的任何标准（`ROLE-LIMIT.md` RN4）。

## 1. 怎么添加（三步）

1. **复制** `USER-TEMPLATE.md`，改名为 `USER-<两位序号>-<短标题>.md`
   例：`USER-01-no-blocking-calls.md`、`USER-02-中文注释必须写清楚单位.md`
2. **填写**模板中的字段（至少填写：标题、适用范围、级别、检查项、依据/理由）。
3. **保存即可，无需通知任何人**。下一轮审查自动生效。

> 想改或想删？直接改、直接删（或把 `级别` 改成 `停用` 并保留文件，便于追溯）。
> 你的标准**优先级最高**：与项目契约冲突时以你为准，`code_reviewer` 只能发 ISSUE 说明冲突，不能拒绝执行。

## 2. 写法要求（为了"可执行"，不是为了形式）

- **每条检查项必须是可判定的**：能回答"是 / 否 / 不适用"，而不是"好不好"。
- **必须写"依据 / 理由"**：这一栏是给 `developer` 看的。它决定了对方是否心服；没有理由的检查项会让返工变成对抗。
- **级别要克制**：只有"确实会出错或违反你的硬要求"的才写 BLOCKER / MAJOR。写得太高的标准会被执行者视为噪音——
  这不是 `code_reviewer` 能替你解决的问题。
- **一次只写一件事**。一条标准里塞五件事，会导致部分执行、部分遗漏。

## 3. 字段速查

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | 是 | `USER-<序号>`，与文件名一致 |
| `title` | 是 | 一句话说清要检查什么 |
| `scope` | 是 | 适用语言 / 目录 / 文件类型；写 `all` 表示全部 |
| `severity` | 是 | BLOCKER / MAJOR / MINOR / NIT（含义见 `../SEVERITY.md`） |
| `status` | 是 | `active` / `inactive`（停用但保留） |
| `rationale` | 是 | **为什么**要检查这一条（给 developer 看的） |
| 检查项 | 是 | 逐条列出，要求可判定 |
| 正例 / 反例 | 建议 | 各给一条，能大幅降低沟通成本 |

## 5. code_reviewer 的义务（供你核对它是否履行）

1. 每次审查**必须**扫描本目录并在报告的"应用标准清单"中**逐条列出本次实际应用的用户标准**（无则写明"无"）；
2. 发现项若与本目录标准相关，**必须**引用你的编号（如 `USER-01`）；
3. 认为你的某条标准有问题时，**只能发 ISSUE 建议**，不得擅自停用或降低级别；
4. 报告未列出用户标准清单 → 该报告**不合格**，你可以要求重做（这是可审计的：报告字段是冻结的）。
