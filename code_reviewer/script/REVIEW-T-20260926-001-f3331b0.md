### F-1【严重/MAJOR】多进程并发 + 轮转组合场景下，已确认写成功的事件被静默销毁（Windows 实证；Linux 行为 unverified）

- **位置**: `developer/script/rmlog/writer.py:217-244`（`_rotate_if_needed`：close→rename 链→reopen，跨进程无任何协调）；`developer/script/rmlog/rmlog.c:283-308`（`rmlog__rotate_locked` 同构）；相关联 `writer.py:169-170`（"轮转放在解锁之后……在持文件锁期间做会让解锁落在错误的新 fd 上"——只考虑了本进程的锁，未考虑他进程 fd）。
- **现象**: 两个进程对同一日志目录以同一 `max_bytes`（触发轮转）并发写入时，一个进程的全部写入（其 `event()` 全部返回 True、退出码 0、`write_failures=0`）可从磁盘上完全消失，且无任何半行、无任何错误信号。对照组（同负载、不触发轮转）600/600 全部完好。
- **复现路径**（本角色验证副本 `code_reviewer/script/_verify_T-20260926-001/r2/` 内实测，脚本与输出均已留档）:
  1. `probe_1e.py` / `probe_1fg.py`：两个 `python -m rmlog.worker <dir> 300 1200`（max_bytes=1200 触发轮转，keep=3）并发写各 300 条；
  2. 结果 A（probe_1e）：总幸存 71 行，**其中一个 worker（300 条全部写成功）幸存 0 行**；结果 B（probe_1g 复跑）：幸存 63 行，同样一个 worker 全灭——**可复现**；
  3. 对照（probe_1f，max_bytes 缺省 8MB 不轮转）：600/600 全部幸存、无空洞、无半行；
  4. 单进程基线（probe_1e solo，300 条+轮转）：幸存 48 行为连续后缀 [252..299]、无空洞——单进程轮转本身正确。
- **推演链**: 轮转协议是"close 自己的 fd → rename 链 → reopen"，对其他进程的 fd 与 `_bytes` 副本零感知。A 进程轮转 rename `rmlog.log→.1` 后，B 进程的 fd 仍绑在旧 inode 上（继续写一个已改名的文件），且 B 的 `_bytes` 计数不随之变化；B 下一次轮转基于陈旧计数提前触发，其 rename 链与 A 的 rename 链交错、`os.remove(oldest)`/"最老副本直接删除"会把 B 搁浅在旧 inode 上的一段**新近数据当作最老副本删除**。两进程轮转窗口交叠（各自每约 25 行轮转一次）时该机制反复发生。Windows 开发机上 os.replace 对他进程打开中的文件失败，使交错序列进一步恶化（probe_1c 显示单侧轮转时 rename 全部失败、数据保全；双侧轮转时出现全灭）。Linux 上 rename 总能成功，推演为"数据随旧 inode 移入副本链、后被 remove(oldest) 淘汰"与"链操作交错产生副本错位"的混合——**未实测，标 unverified**（见 §6）。
- **依据条款**: `standard/SEVERITY.md` §1 MAJOR（"在特定但现实的条件下出错"+ 数据损坏性质；反向规则禁止降级）；`REQ-20260926-001-logging.md` §4 P0-d（"可靠落盘……多进程并发写不产生交错半行"——组合场景虽不在 AC5 字面演示配置内，但"多进程+轮转"是 P0 已交付能力的自然组合，且 `worker.py:28` 自述 max_bytes 参数就是为"压测轮转竞争路径"而设）；`CHECKLIST-COMMON.md` GEN-08（并发共享状态保护）、GEN-14（部分失败留下半完成状态）。
- **级别: 严重（MAJOR）**。建议（方向性，由 developer 决定方案）：多进程轮转需跨进程协调（如 Linux 才启用轮转/轮转区纳入跨进程互斥/rename 前后做存活校验），或在文档与 IMPL 中明确"轮转仅支持单写者场景、多写者必须停写轮转"，并把"多进程+轮转"组合用例补入 selftest；同时将本发现与 AC5 的关系提交 management 判定是否影响验收投入。

### F-2【严重/MAJOR】读端 `filter --until` 接受分钟级前缀却系统性漏掉该分钟的全部事件——按 USAGE §5 演示用法操作会漏证据

- **位置**: `developer/script/rmlog_read.py:151-153`（`--since/--until` 原样字符串比较）；佐证 `rmlog_read.py:132-135`（docstring："wall_ts 是定宽 ISO8601, 字典序即时间序"——设计前提是同宽，但未对前缀做处理）；`developer/script/USAGE.md:129`（"用比赛时间窗收窄（--since/--until 传墙上时间前缀即可）"并给出分钟级示例 `--until 2026-09-26T14:38`）。
- **现象**: `--until 2026-09-26T12:01` 只返回 12:00 的行，12:01 这一分钟的全部行（含 12:01:00.500 这第一条）都不命中；`--since 2026-09-26T12:01` 前缀则正确包含整分钟。
- **复现路径**（probe_until2.py，留档）: 构造 3 行合法日志（12:00:00.100 / 12:01:00.500 / 12:01:59.900）→ `filter --until 2026-09-26T12:01` 实得 1 行（期望 2）→ `filter --until 2026-09-26T12:01:59.900` 实得 3 行（全精度正确）→ `filter --since 2026-09-26T12:01` 实得 2 行（正确）。
- **推演链**: "12:01:00.500" <= "12:01" 按字典序为 False——`--until` 是上界比较，截断前缀会整体小于该前缀分钟内的任何完整时间戳。USAGE §5 的 5 分钟定位演示第 3 步正是分钟级 `--until`，比赛时间窗的最后一个分钟事件会**静默漏掉**（无警告、无计数），取证者以为"窗口内没有错误"。

- **级别: 严重（MAJOR）**。建议：对 `--since/--until` 做前缀归一（`--until` 截断前缀视为"该前缀段末"——补齐 `.999…`）或在参数校验时拒绝非全精度值并在 USAGE 更正示例；补一条分钟前缀回归用例进 selftest。

- **依据条款**: `CHECKLIST-COMMON.md` GEN-10/11/13（失败检查/上报路径/吞错）、GEN-26（注释与代码一致）；`developer/script/CODE-STYLE.md` §4.1、`writer.py` 自身接口契约；`SEVERITY.md` §1 MINOR（不影响当前主路径正确性、影响健壮性且有条款）。
