# 角色注册表 (Role Registry)

> 维护者: framework_admin · 任何角色变更必须先在此登记

## 命名规范

- 文件夹名：小写 + 下划线，例如 `framework_admin`、`data_curator`、`report_writer`。
- 角色代号：与文件夹名一致，邮件中用 `to: <role_code>`。
- 角色 ID：`R-001` 递增编号，永不复用。

## 三层结构与指挥链（R-001 / R-002 / R-003）

| 层 | 角色 | 与被谁指挥 |
|---|---|---|
| 委托层 | 人类用户 | 最高决策权。项目需求 → R-002；架构 / 角色 / 规范 → R-001 |
| 治理层（元层） | R-001 `framework_admin` | **不被任何人指挥，也不指挥执行层**；只定义"谁能做什么"，不决定"这次谁做什么"；对边界 / 接口 / 规范争议有仲裁权 |
| 执行层 | R-002 `management` | 不服从 R-001；**指挥 R-003**（任务编排：派活 / 催办 / 验收 / 打回） |
| 执行层 | R-003 `developer` | **服从 R-002**（仅限 WHAT / WHEN）；与 R-001 **平行同级、无指挥链**；技术实现（HOW）自主 |
| 执行层·校验 | R-004 `code_reviewer` | 受 R-002 的任务编排（**审什么、何时审**），但**审查结论完全独立**；与 R-001 无指挥链；与 R-003 互为独立双方（**不得修改对方产物**） |
| 执行层·验证 | R-005 `software_tester` | 受 R-002 的任务编排（**要不要测、测什么、何时测**），但**环境与方法自主、运行结果只受证据影响**；与 R-001 无指挥链；与 R-003 **互为独立双方（不得修改对方产物）** |

> **两条独立验证通道（R-004 与 R-005）**：`code_reviewer` 做**静态审查**（读代码，回答"代码在标准下有没有问题"）；
> `software_tester` 做**动态运行**（跑程序，回答"程序实际跑起来是什么结果"）。**两者互不替代，也互不指挥。**

> **审查门（`00-ARCHITECTURE.md v1.1 §4.1`）**：R-003 的每一轮代码交付**必须**先经 R-004 独立审查，方可进入 R-002 的验收。
> 门是**强制**的，违规码 **V7（绕过审查）**。审查者的独立性用一句话表述：**"你可以要求我审，不能要求我过。"**
>
> **框架中第一条真实指挥链：R-002 → R-003。** 此前 R-001/R-002 之间为"平行同级、无指挥链"。
> 指挥链的**范围**被严格限定为 WHAT / WHEN；HOW 属 R-003 的专业自主（理由：R-002 无技术专业身份，其 MN2 已禁止其做业务判断）。
> 该裁定为**约束性仲裁结论**，见 `_framework/decisions/DECISION-20260923-003-developer-role-adopted.md §3`。

## 层级与权限声明（R-001 / R-002）

| 声明 | 内容 |
|---|---|
| 同级关系 | R-001 与 R-002 **平行同级**，两者之间**无上下级指挥链**，只有职责分工 |
| 分工轴 | R-001 管"**谁能做什么**"（角色与边界，元层/静态）；R-002 管"**这次谁做什么**"（任务与顺序，执行层/动态） |
| 建角色权 | **唯一属于 R-001**。R-002 只能发 TASK 请求（M10），且请求可被驳回 |
| 仲裁权 | 边界/接口/规范争议归 **R-001**（架构 §6.4）；项目执行内的调度争议归 **R-002** 自行裁量 |
| 失能判定 | 角色长期无响应的**催办权**归 R-002（≤2 次）；**失能判定与介入权**归 R-001（架构 §5.4） |
| 用户接口 | 项目需求 → R-002；架构/角色/规范请求 → R-001。错投方须在 1 轮内转派并回信 |

## 边界正交性自检（framework_admin 必做）

对任意两个角色 A、B，检查是否存在动作 X 使得 X 同时落在 A 的"只能做"与 B 的"只能做"中。
若存在，必须指定**唯一主责方**，另一方降级为"仅可建议"。
