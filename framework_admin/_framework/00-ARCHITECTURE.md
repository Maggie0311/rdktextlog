# 多角色协作框架 · 总架构规范

> 版本: v1.0 · 生效日期: 2026-02-14 · 维护者: framework_admin · 状态: 生效中
> 本文件是**根规范**。任何角色文件夹内的规则若与本文件冲突，以本文件为准；framework_admin 负责仲裁与修订。

---

## 1. 设计目标

把一项长期工程拆成**若干互相独立、边界清晰、可被审计的角色**，每个角色像一只动物一样拥有：
记忆、注意力聚焦点、本能边界（不越界）、以及与外界的通信渠道。

解决三个经典失效模式：
1. **越权**：一个角色干了别的角色的活，导致冲突与重复。
2. **失忆**：每个新任务从零开始，重复犯同样的错。
3. **失联**：角色之间不通信，产出对不上接口。

---

## 2. 角色文件夹标准结构（强制）

```
<role_name>/
├── mailbox/                 通信邮箱（唯一跨角色通道）
│   ├── inbox/               来信（未处理 -> 处理后移入 archive）
│   ├── outbox/              待发/已发（发出的信留副本）
│   ├── archive/             已归档（按 YYYY-MM 分子目录）
│   └── drafts/              未定稿草稿
├── memory/                  记忆系统（分层，仿动物记忆）
│   ├── long-term/           长期记忆：经反复检验沉淀的信念
│   ├── short-term/          短期记忆：近若干次任务的工作记忆
│   └── index/               索引与置信度总表（MEMORY-INDEX.md 等）
├── role-limit/              职责边界：只能做什么 / 绝不能做什么
├── principles/              专业原则：本角色的专长与注意力焦点
├── script/                  脚本与产出物（可复现的资产）
├── plan/                    任务前规划（PRR 计划）
└── worklog/                 工作日志（分条、可审计）
```

**七个目录一个都不能少**，即使暂时为空也要有 `README.md` 占位，说明该目录的用途与写入规则。

---

## 3. 七目录职责一览

| 目录 | 回答的问题 | 写入者 | 生命周期 |
|---|---|---|---|
| mailbox | 别人要我知道什么？我要别人知道什么？ | 双方 | 处理完即归档 |
| memory/long-term | 我**确信**的、跨任务可复用的经验 | 仅晋升流程 | 长期，可被降级 |
| memory/short-term | 我最近几次任务学到了什么？ | 角色自身 | 滑动窗口，会被遗忘 |
| role-limit | 我**只能**做什么、**绝不能**做什么 | framework_admin | 稳定，变更需版本化 |
| principles | 我靠什么**专业**判断做事 | framework_admin + 角色沉淀 | 半稳定 |
| script | 我**产出**了什么可用东西 | 角色自身 | 长期，按版本管理 |
| plan | 我这次**打算怎么做** | 角色自身 | 每任务一份 |
| worklog | 我**实际做了什么**、为什么 | 角色自身 | 只追加，不修改 |

## 4. 角色的标准工作循环（Run Loop）

每个角色接活后，**严格按此顺序**执行，不得跳步：

```
0. 开工前置  : 读 inbox -> 读 memory/long-term -> 读 memory/short-term -> 读 role-limit -> 读 principles
1. 规划      : 在 plan/ 写下 PRR 计划（目标/约束/依据/步骤/接口/验收/回滚）
2. 通信      : 向所有依赖方/被依赖方发 MAIL（TASK 或 QUERY 或 NOTIFY）
3. 执行      : 只在 role-limit 允许的范围内动手
4. 记录      : 同步追加 worklog/（分条、带时间戳、带理由）
5. 产出      : 产物落 script/，按命名规范登记
6. 交邮      : 向消费方发 RESULT/HANDOFF 邮件；阻塞则发 ISSUE
7. 记忆      : 写 short-term；触发晋升/衰减判定（见 memory 模型）
8. 归档      : inbox 处理完的信移入 archive
```

> **硬性要求**：第 0 步与第 7 步是强制项。未读记忆就开工、或干完不留记忆，视为流程违规。

## 6. 冲突与仲裁

1. 边界争议：以 `role-limit/` 文本为准；文本未覆盖时，默认**不做**，先发 QUERY 给 framework_admin。
2. 接口争议：以 `_framework/02-MAILBOX-PROTOCOL.md` 定义的消息契约为准。
3. 记忆争议：以 `_framework/03-MEMORY-MODEL.md` 的置信度与晋升规则为准。
4. 最终仲裁人：framework_admin。仲裁结果必须写入 `_framework/decisions/`。

---

## 7. 违规判定（审计项）

- V1 越界：执行了 role-limit 中"绝不能做"清单里的事项。
- V2 无计划：plan/ 中无对应 PRR 就产生产物。
- V3 无日志：worklog/ 中查不到对应动作记录。
- V4 断链：产出了交付物却未向消费方发 MAIL。
- V5 记忆污染：把未经检验的猜测直接写入 long-term。
- V6 静默修改：修改了他人的文件/契约而未发 NOTIFY。

审计由 framework_admin 执行，违规记入 `_framework/decisions/AUDIT-LOG.md`。
