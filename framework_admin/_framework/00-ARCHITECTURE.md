# 多角色协作框架 · 总架构规范

> 版本: **v1.2** · 生效日期: 2026-02-14
> v1.1 修订: 2026-09-23（新增 §4.1 审查门 与 违规码 V7）· **v1.2 修订: 2026-09-25（新增 §2.1 角色自足原则，废止一切公共工作空间）** · 维护者: framework_admin · 状态: 生效中
> 本文件是**根规范**。任何角色文件夹内的规则若与本文件冲突，以本文件为准；framework_admin 负责仲裁与修订。

---

## 1. 设计目标

把一项长期工程拆成**若干互相独立、边界清晰、可被审计的角色**，每个角色像一只动物一样拥有：
记忆、注意力聚焦点、本能边界（不越界）、以及与外界的通信渠道。

解决三个经典失效模式：
1. **越权**：一个角色干了别的角色的活，导致冲突与重复。
2. **失忆**：每个新任务从零开始，重复犯同样的错。
3. **失联**：角色之间不通信，产出对不上接口。

## 2. 角色文件夹标准结构（强制）

```
<role_name>/
├── mailbox/                 通信邮箱（唯一跨角色通道）
│   ├── inbox/               来信（未处理 -> 处理后移入 archive）
│   ├── outbox/              待发/已发（发出的信留副本）
│   ├── archive/             已归档（按 YYYY-MM 分子目录）
│   └── drafts/              未定稿草稿
├── memory/                  记忆系统（分层，仿动物记忆）
│   ├── long-term/           长期记忆：经反复检验沉淀的信念
│   ├── short-term/          短期记忆：近若干次任务的工作记忆
│   └── index/               索引与置信度总表（MEMORY-INDEX.md 等）
├── role-limit/              职责边界：只能做什么 / 绝不能做什么
├── principles/              专业原则：本角色的专长与注意力焦点
├── script/                  脚本与产出物（可复现的资产）
├── plan/                    任务前规划（PRR 计划）
└── worklog/                 工作日志（分条、可审计）
```

**七个目录一个都不能少**，即使暂时为空也要有 `README.md` 占位，说明该目录的用途与写入规则。

### 2.1 角色自足原则（No Shared Workspace）— v1.2 新增

> **一句话不变量：每一块区域有且仅有一个写入者；本框架不存在"公共工作空间"。**

1. **角色目录自足**：每个角色的**全部产物**（含交付代码、报告、脚本、打包件）都落在**该角色自己的目录**内，
   主要是 `script/`。**不存在任何多个角色都能写的区域。**
2. **跨角色流转只经邮箱**：产物交付 = 发信（`RESULT` / `HANDOFF`）+ 给出**路径**与 **commit hash**（+ 可选打包件，写入 `attachments`）。
   需要他方改动 → 发 `ISSUE` / `TASK`，**不得直接写**。
3. **受限的是"写"，不是"读"**：审查（`code_reviewer`）、验收（`management`）、审计（`framework_admin`）
   需要读取他方产物，属**正常且必要**。本条禁止的是**跨角色的写入**，不是只读访问。
4. **单主区不是公共区**：`_framework/` 由 `framework_admin` 独占、各角色目录由其本人独占——
   其余角色只读。它们**各有唯一写入者**，因此不构成本条所禁止的"公共工作空间"。
5. **判据（可当场回答）**：指着任意一个目录问——**"这块区域有几个写入者？"**
   答案是 1 → 合规；答案是 ≥2 或"谁都行" → **违规设计，必须拆分或并入某个角色的目录**。

**为什么**（这是本原则的存在理由，写下来是为了防止日后被当成形式主义）：
公共工作空间会让**边界变模糊**——"这块归谁"无法再用目录回答，只能靠记忆与口头约定；
而一旦两个角色都能写同一处，就必然出现**并发写、互相覆盖、责任不清**。
目录归属一旦清晰，越界判定就退化为一条**路径判断**，无需争论。

> **历史依据**：v1.0 期间曾设立过 `src/` 作为跨角色共享产物区，因其与本节原则相悖已被
> `DECISION-20260924-005` 废止（详见该文件 §3 的自我评估：那不是口味差异，是自相矛盾）。

## 3. 七目录职责一览

| 目录 | 回答的问题 | 写入者 | 生命周期 |
|---|---|---|---|
| mailbox | 别人要我知道什么？我要别人知道什么？ | 双方 | 处理完即归档 |
| memory/long-term | 我**确信**的、跨任务可复用的经验 | 仅晋升流程 | 长期，可被降级 |
| memory/short-term | 我最近几次任务学到了什么？ | 角色自身 | 滑动窗口，会被遗忘 |
| role-limit | 我**只能**做什么、**绝不能**做什么 | framework_admin | 稳定，变更需版本化 |
| principles | 我靠什么**专业**判断做事 | framework_admin + 角色沉淀 | 半稳定 |
| script | 我**产出**了什么可用东西 | 角色自身 | 长期，按版本管理 |
| plan | 我这次**打算怎么做** | 角色自身 | 每任务一份 |
| worklog | 我**实际做了什么**、为什么 | 角色自身 | 只追加，不修改 |

## 4. 角色的标准工作循环（Run Loop）

每个角色接活后，**严格按此顺序**执行，不得跳步：

```
0. 开工前置  : 读 inbox -> 读 memory/long-term -> 读 memory/short-term -> 读 role-limit -> 读 principles
1. 规划      : 在 plan/ 写下 PRR 计划（目标/约束/依据/步骤/接口/验收/回滚）
2. 通信      : 向所有依赖方/被依赖方发 MAIL（TASK 或 QUERY 或 NOTIFY）
3. 执行      : 只在 role-limit 允许的范围内动手
4. 记录      : 同步追加 worklog/（分条、带时间戳、带理由）
5. 产出      : 产物落 script/，按命名规范登记
6. 交邮      : 向消费方发 RESULT/HANDOFF 邮件；阻塞则发 ISSUE
7. 记忆      : 写 short-term；触发晋升/衰减判定（见 memory 模型）
8. 归档      : inbox 处理完的信移入 archive
```

> **硬性要求**：第 0 步与第 7 步是强制项。未读记忆就开工、或干完不留记忆，视为流程违规。

### 4.1 审查门 (Review Gate) — v1.1 新增

某些交付物必须先经过**独立审查**才能进入验收。**受约束的交付物由 `_framework/decisions/` 中的 DECISION 指定**
（当前：**R-003 `developer` 的每一轮代码交付，须经 R-004 `code_reviewer` 审查**）。

1. **触发**：交付角色**每完成一轮工作**（一个 `task_id` 的交付），**必须**先向审查角色发起审查请求，
   **再**向 management 报 RESULT。两者顺序不可颠倒。
2. **禁止绕过**：不得在缺少本轮审查报告的情况下进入验收；不得以"改动很小""时间紧""已经来回好几次了""我记得没问题"为由跳过。
   违规码 **V7**。
3. **验收前置**：`management` 不得在下列情形判 `accepted`——(a) 缺少本轮审查报告；(b) 审查结论为"不通过"且阻断级问题未修复。
   **唯一例外**：人类用户以书面形式（邮件或 `_framework/decisions/`）明确接受该风险，并写明理由与时限。
4. **结论独立于指令**：审查角色服从"**审什么、何时审**"，但**审查结论只受证据影响，不受指令影响**。
   任何要求修改结论的指令一律无效，只能通过补充证据或走升级路径来解决。
5. **审查者不修码**：审查者只出结论与证据，**修复由交付角色完成**。审查者不得改动被审代码（否则既当运动员又当裁判）。
6. **审查对象必须冻结**：审查报告须记录被审对象的 **commit hash**。报告出具后代码若发生变化，该报告**即行失效**，
   须重新审查（增量审查即可，但必须重新出结论）。
7. **分支规则**：报告与结论的**主送方是交付角色**，**抄送 management**（门是验收前置，故它必须收到）。

> **为什么立在根规范**：审查门是**跨角色**规则，且约束双方（交付方与验收方）。按 P10 规范性递减，跨角色规则必须落在根层，
> 不得塞进任一角色的私有契约——否则任一方修改自己的契约即可绕开。

## 6. 冲突与仲裁

1. 边界争议：以 `role-limit/` 文本为准；文本未覆盖时，默认**不做**，先发 QUERY 给 framework_admin。
2. 接口争议：以 `_framework/02-MAILBOX-PROTOCOL.md` 定义的消息契约为准。
3. 记忆争议：以 `_framework/03-MEMORY-MODEL.md` 的置信度与晋升规则为准。
4. 最终仲裁人：framework_admin。仲裁结果必须写入 `_framework/decisions/`。

---

## 7. 违规判定（审计项）

- V1 越界：执行了 role-limit 中"绝不能做"清单里的事项。
- V2 无计划：plan/ 中无对应 PRR 就产生产物。
- V3 无日志：worklog/ 中查不到对应动作记录。
- V4 断链：产出了交付物却未向消费方发 MAIL。
- V5 记忆污染：把未经检验的猜测直接写入 long-term。
- V6 静默修改：修改了他人的文件/契约而未发 NOTIFY。
- V7 绕过审查：交付物未经独立审查即进入验收；或审查结论被非证据因素（指令、人情、进度压力、"来回次数太多"）修改或放行。
  判定方法：取任一受 §4.1 约束的交付，检查是否存在与其 commit hash 对应的审查报告，且报告结论为通过（或缺席时有用户书面风险接受）。

> **关于"授权"的界定（v1.2 补注）**：因本框架**不存在公共工作空间**（§2.1），
> 对非自有区域的写入**没有"公共区"这一豁免路径**。除根规范明确授予的写入权外
> （例如 `framework_admin` 的 A2 对任意角色 `role-limit/`、`principles/` 的签发权，A6 对任意角色 `mailbox/inbox/` 的投递权），
> 一切对非自有区域的写入均按 V6 判定。

审计由 framework_admin 执行，违规记入 `_framework/decisions/AUDIT-LOG.md`。
