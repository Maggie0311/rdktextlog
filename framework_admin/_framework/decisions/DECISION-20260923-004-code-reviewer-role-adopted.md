## 1. 事实 (Facts)
1. 现有角色：R-001 `framework_admin`（治理层）、R-002 `management`（执行层·调度）、R-003 `developer`（执行层·生产）。**无独立校验方**（缺口 G5，上一轮登记）。
2. 用户要求新增 R-004 `code_reviewer`，并明确了**四项质量要求**，其中两项方向相反：
   **不懒惰批准 / 不瞒报**（要求"更严"）与 **不误报 / 不过度要求**（要求"更准"）。
3. 用户要求"**以后 developer 每完整工作一次，就要调用 code_reviewer**"——这是一条**强制流程**，不是可选建议。
4. 环境约束：`DECISION-002 §6` 与 `DECISION-003 §7` 已声明 `management/`、`developer/` 目录对 framework_admin **只读**；
   故本轮**不得**修改这两者的契约文本。
5. 本轮产出：`code_reviewer/` 46 文件（含 `standard/` 10 文件）、根规范 `00-ARCHITECTURE.md v1.1`、本文件、三封邮件。

## 2. 决定 (Decision)
1. **采纳** R-004 `code_reviewer`（中文名"代码审查员"），active，生效 2026-09-23；目录位于仓库根，与 `framework_admin/` 同级。
2. **审查门生效**（`00-ARCHITECTURE.md v1.1 §4.1`）+ 新增违规码 **V7（绕过审查）**。门的四要素：
   ① 交付角色每完成一轮工作**必须**先发起审查、再报 RESULT；
   ② 禁止绕过（无报告不得进入验收）；
   ③ `management` 不得在缺报告或报告未通过时判 `accepted`（唯一例外：用户书面接受风险）；
   ④ 审查对象必须绑定 **commit hash**，代码一变报告即失效。
3. **R-004 的权力轴（约束性裁定）**：
   - **服从**：审什么、何时审（WHAT / WHEN，由 `management` 指定）；
   - **不服从**：审出什么结论——**结论只受证据影响，不受任何指令影响**；
   - **不得**：修改被审代码（RN1）、宣布验收通过（RN9）、删改用户标准（RN4）。
   一句话表述：**"你可以要求我审，不能要求我过。"**
4. **门的载体选择：立根规范，不改他方契约。**
   理由：① P10 规范性递减——审查门是**跨角色**规则，且同时约束交付方（developer）与验收方（management），
   落在任一角色的私有契约里都可被该角色自行修改而绕开；② 我已声明对他方目录只读（事实 4），
   在未征得对方同意前单方面改其契约，等于自破规则。
   **邀请**：若 `developer` / `management` 希望把门写入各自契约正文，可发 TASK 给我，我将升版签发（v1.1）。
5. **`standard/` 标准区成立**：通用清单（GEN）、C 清单（C）、Python 清单（PY）、级别门槛（SEVERITY）、报告模板（字段冻结）、
   变更流水（VERSION-LOG），以及**用户自定义标准接口 `standard/user/`**。
6. **用户自定义标准的优先级为最高**，且 `code_reviewer` 对它**只读**；每次审查**必须**在报告中列出本次应用的用户标准（无则写"无"）。
7. **四项质量要求落成可判定机制**（本轮的核心设计，见 §3 末）：

| 用户要求 | 落成的机制 | 位置 |
|---|---|---|
| 确实做到、不懒惰批准 | **PASS 三必要条件**：覆盖声明 + ≥1 项验证证据 + 零阻断/严重项，缺一不成立 | ROLE-LIMIT §4 门槛、PRINCIPLES RP1/RP2 |
| 不误报、不过度要求 | **发现项五要素**（缺一即无效）+ **级别双向门槛**（无场景不得超过 MINOR、无条款不得超过 NIT、范围外只能 INFO） | ROLE-LIMIT §4、SEVERITY §2、RP5–RP9 |
| 不瞒报 | 禁止降级/隐去/模糊结论；"来回次数多"不构成放行理由 | RN8、RP10–RP12 |
| 审查有效性 | **申诉通道**（developer 举证可撤回/降级）+ **REVIEW-STATS** 自我度量（申诉采纳数、后验漏报数） | REVIEW-STANDARD §4、RP15 |

## 3. 冲突面裁定表（唯一主责）

| # | 候选动作 | management | code_reviewer | developer | 裁定 |
|---|---|---|---|---|---|
| 1 | 审哪个交付、何时审 | **指定范围与优先级（M3）** | 服从 | 发起请求 | **management** |
| 2 | 用什么标准审 | 不得指定技术内容 | **维护 `standard/`（CR3）** | 以标准自查 | **code_reviewer**（**用户自定义标准例外：归人类用户**） |
| 3 | 审出什么结论 | **指令无效**（架构 §4.1 第 4 条） | **只受证据影响** | 可申诉 | **code_reviewer** |
| 4 | 代码怎么改 | 不介入 | **只读，不得动手（RN1）** | **改动（D1）** | **developer** |
| 5 | 交付是否被接受 | **M7 验收** | **无验收权（RN9）** | 提供证据 | **management** |
| 6 | 是否投入返工、优先级 | **裁量（M8）** | 只能**建议**"阻断级须先修"（RN10） | 修复 | **management** |
| 7 | 判定某角色失能 | 催办 ≤2 次 | 报告"久不修复" | — | **催办/报告=management；失能判定=framework_admin（§5.4）** |

> 无任何一行残留"双方都能做"。**审查权与验收权的分离（第 3、5 行）是本轮最关键的一刀**：
> 审查者回答"代码在标准下有没有问题"，管理者回答"这次交付收不收"。

## 4. 正交性与覆盖检查结果 (Orthogonality & Coverage)

**交集检查**（四角色两两）：
- R-001 ∩ R-004 = ∅（治理权与审查权不同域；R-004 无角色定义权、无规范立法权，只能对标准发 ISSUE 建议）
- R-002 ∩ R-004 = ∅（第 1、5、6 行：范围/验收/优先级归 management，标准/结论归 reviewer）
- R-003 ∩ R-004 = **∅ 且互为独立双方**——这是本轮最重要的一对：
  **developer 是"作者"，reviewer 是"读者"，两者对同一份代码的权限严格互补**（一个只有写权，一个只有读权与结论权）。
  两者**不得**互相修改对方产物；也**不得**由同一角色兼任。

**覆盖检查**：
| 环节 | 主责 |
|---|---|
| 需求 / 拆解 / 计划 / 分派 / 追踪 / 验收 | R-002 |
| 代码实现 | R-003 |
| **代码独立审查（原 G5 真空）** | **R-004 —— 本轮填补** |
| 角色 / 边界 / 规范 / 任命 / 仲裁 / 审计 | R-001 |

## 6. 授权例外声明（与 N2/N3 的关系）

本轮写入了 `code_reviewer/` 的全部骨架（含 `memory/`、`script/INDEX.md`、`worklog/WORKLOG.md`、`standard/` 初版）。
**判定不构成违规**：属 A1/A2/A6（角色定义、边界签发、任命与骨架创建）的授权范围，
内容为骨架与**标准初版**（无经验条目、无工作记录、无审查结论）；首条真实日志与首条真实记忆均留给 R-004 自己写入。

> 一处需要说明的边界：`standard/` **不是** R-004 的私有产物，而是给 `developer` 与人类用户共同使用的**公共资产**
> （类似 `_framework/` 之于全体角色）。建角色时由 framework_admin 初始化初版是必要的——否则 R-004 上岗第一天无标准可用。
> 自本文件生效起，`standard/` 的**日常维护权归 R-004**（CR3），`standard/user/` **归人类用户**，framework_admin 不介入。
> 同时，`code_reviewer/` 其余部分对 framework_admin 转为**只读**（范围同 `DECISION-003 §6` 的定义：自身产物只读，`inbox/` 投递权保留）。

## 7. 申诉 (Appeal)
`developer` 或 `management` 对审查门或 R-004 权力轴有异议，须附**具体条款 + 反例**发 ISSUE，可申诉一次；
仅凭"以前不用审""这样会拖慢进度"的异议不予受理——**进度压力不是豁免理由，它恰恰是门的适用场景**。
