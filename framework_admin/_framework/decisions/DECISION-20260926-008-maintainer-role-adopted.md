## 1. 事实 (Facts)
1. 现有角色：R-001 治理 / R-002 调度 / R-003 生产 / R-004 静态审查 / R-005 动态测试。
   **无任何角色负责"让人类看懂代码、并把合格产物长期守住"**——这是一条此前完全空缺的环节。
2. 委托层明确指出本角色的定位：**"代码 ↔ 人的理解"之间的接口**，服务于**长期维护与最终裁决**。
3. framework_admin 发起 `ask_user_question`（6 个待定设计问题）时**调用超时**（10 分钟无响应）；
   为不空转，核心功能按委托层原话直接落地，六项待定项**按推荐默认值落地并标注待确认**（见 §3）。

## 2. 决定 (Decision)
1. **采纳** R-006 `maintainer`（中文名"代码维护者"），active，生效 2026-09-26；目录位于仓库根，与 `framework_admin/` 同级。
2. **职责四件套**（委托层原话的落地）：**冻结归档 / 解释（说明书）/ 补注（不碰代码）/ 答疑**；
   并支撑**长期维护**（版本脉络、墓碑记录、教学向产物接口）。
3. **归档触发（硬性）**：`developer` 与 `software_tester` 的**合格确认通知齐备**，且**两封 commit hash 一致**；
   缺一封 → 发 `QUERY`，**不得先归档后补**。`management` 的验收结论**事后回填**版本卡（归档**早于**验收，
   以便人类拿着说明书做最终裁决）。
4. **"不修改源代码"与"补充注释"同时成立的方式**：**原件按字节冻结归档 + 另存带注副本**。
   带注副本 vs 原件的 **diff 必须只含新增注释行**（§4 补注判定表）；该结论记入版本卡。
5. **`code_archive/` 位于 `maintainer/` 目录内**（`maintainer/code_archive/`）：
   符合 §2.1"无公共工作空间"（唯一写入者是 maintainer）；**与 `mailbox/archive/` 严格区分**
   （前者按 `task_id` + 版本组织、归档**代码**；后者按 `YYYY-MM` 组织、归档**邮件**）。
6. **不做质量裁定、不做验收**：质量判断归 R-004（静态）/ R-005（动态）；验收归 R-002 与人类用户。
   发现疑点只按 K11 报"疑似"（附位置与理由），**不修、不裁定**。
7. **本角色的核心风险条款**：**错误的解释比没有解释更危险**（人类会据此维护与裁决）。
   故说明书强制包含**事实层与推断层的分离声明**与**未解疑问（`unverified`）**两节——**未解疑问必须列出，禁止省略**。
8. **新义务已签发进三个既有角色的契约**（依据 §2.1.1 义务闭合性，**不得只由我的档案承载**）：

| 角色 | 新增义务 | 落点 |
|---|---|---|
| `developer` | 交付**通过审查且自测通过**后，向 `maintainer` 发合格确认通知（含 `task_id` / commit hash / 路径 / 构建方式 / 自测证据 / 审查报告路径）；顺序：**审查 → 通知 maintainer → 报 RESULT** | `developer/role-limit` §2.1.5 |
| `software_tester` | 测试**未发现阻断级问题**时发合格确认通知（含测试范围 / 报告路径 / **未覆盖项**）；**发现阻断问题时不得发** | `software_tester/role-limit` §2.1.4 |
| `management` | 验收结论（`accepted` / `rejected` 及理由）须在 1 轮内发 `maintainer` 回填版本卡与索引 | `management/role-limit` §2.1.4 |

## 3. 待委托层确认的六项（已按推荐默认值落地，可改）

| # | 待定项 | 采用值 | 备选 |
|---|---|---|---|
| 1 | 归档触发 | 两封通知齐备即归档，验收结论事后回填 | 必须先验收通过才归档 / 单方通知即可 |
| 2 | 补注方式 | 原件冻结 + 带注副本 | 直接在原文件只加注释行（须重新校验并通告） |
| 3 | `code_archive` 位置 | `maintainer/code_archive/` | 仓库根 `code_archive/`（需单独裁定单主归属） |
| 4 | 归档粒度 | 全留历史 + 大文件不入库（存校验值与重建方式） | 大文件一并入库 / 只留最终通过版 |
| 5 | 疑点去向 | 发 ISSUE 给 `developer`（抄 `management`），只报告不修不裁定 | 只写进说明书未解疑问 / 不主动报告 |
| 6 | 附加产物 | **暂不产出，保留接口**（`DIFF` / `WALKTHROUGH` / `GLOSSARY` 已在 `script/README.md` 留位） | 全部启用 / 部分启用 |

## 4. 冲突面裁定表（唯一主责）

| # | 候选动作 | 归属 | 裁定理由 |
|---|---|---|---|
| 1 | **读代码** | R-004 为**判断**而读 / R-005 为**运行**而读 / **R-006 为解释与长期可维护而读** | **产出物性质不同**（判断 / 事实 / 解释），故不重叠——沿用已验证的切分方法（STM-004/006） |
| 2 | **归档代码产物** | **R-006**（唯一写入者） | 其他角色只读；R-006 的 `code_archive/` 不与他人的 `mailbox/archive/` 混用 |
| 3 | **归档邮件** | 各角色自己的 `mailbox/archive/` | 与代码归档的检索维度不同（时间 vs 版本） |
| 4 | **写/改代码** | **R-003** | R-006 对来源**只读**；补注只发生在**自己归档区内的副本**上 |
| 5 | **质量判断** | R-004 / R-005 | R-006 不做裁定，只报疑似 |
| 6 | **验收** | **R-002 + 人类用户** | R-006 不做验收 |
| 7 | **人类关于代码细节与含义的提问** | **R-006**（主责） | 其他角色可答其职责域内的问题（如 R-004 答"为什么判它不通过"），但**代码含义解释**的主责是 R-006 |
