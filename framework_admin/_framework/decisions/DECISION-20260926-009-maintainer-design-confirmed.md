## 3. 执行变更（本轮实际改动）

### 3.1 归档触发 → **验收前置**（三份要件）
- **新顺序**：`developer` 与 `software_tester` 各发**合格确认通知（备料）** → `management` 出 **`accepted` 结论（许可）**
  → `maintainer` **三份齐备**后归档；
- 三份要件的 **commit hash 必须一致**；`management` 判 `rejected` → **不归档**，该版本进 `_tombstones/`；
- **副作用（已如实记入任命信）**：**说明书要等验收通过之后才产生**；验收前人类手上只有审查与测试报告。

**改动落点**：`maintainer/role-limit`（元信息触发依赖 / §0 权力轴 / K1 / 权限矩阵 / KN2 / KN11 / §3 输入契约 / §5 / DoD）；
`management/role-limit §2.1.4`（由"归档回填义务"改为"**归档许可义务**"）；
`developer/role-limit §2.1.5` 与 `software_tester/role-limit §2.1.4`（由"归档移交义务"改为"**归档备料义务**"，并注明许可在 management）。

### 3.2 补注方式 → **就地补注**（单份，不另存副本）
- `code_archive/<task_id>/code/`：从来源**逐字节复制**后，**注释就地加在这些文件上**；
- **冻结的新含义**：补注完成的那一刻起，该文件**一字不改**；要变只能新版本；
- **双指纹（新增要求）**：版本卡记 ① 补注前（来源 commit + SHA-256 清单）② 补注后（SHA-256 清单），
  并附 diff 结论（**只含以注释符号开头的新增行**）。仅凭单份指纹无法证明"只加了注释"，故必须双份；
- 原 `original/` + `annotated/` 双目录结构 → 改为单一 `code/` 目录。

## 4. 一处冲突与我的处理（**需要委托层确认**）

委托层选择"**直接在原文件里只增注释行**"。但委托层的**另一条硬要求**是"不得修改 `developer` 的源代码"，
且 `developer` 的契约规定其 `script/**` 由 developer **独占写入**（`developer/role-limit §2.1.3` 产物自足）。

**framework_admin 的处理**：把"原文件"判定为**归档下来的那份代码文件**（`code_archive/<task_id>/code/`）——
即**就地补注、不另存第二份副本**，而 `developer` 目录中的源文件**仍然一字不动**。

**若委托层的本意是"连 `developer` 目录中的源码也要带注"**，则需**明确授权**：那会同时打破两条不变量
（"来源只读"与"每块区域只有一个写入者"），且带注后的文件与既有**审查报告 / 测试报告所对应的 commit** 不再一致。
届时 framework_admin 将另出裁决，并把该变更**签发**给 `developer`、`code_reviewer`、`software_tester` 三方。
