**审查与测试的基准永远是来源 commit，归档件只供人类阅读**；说明书引用位置须同时给出两个标识。

## 5. 多用户协作评估（你要的探索）

### 结论：**可以多用户协作，但不能"简单共享一个远程仓库、各自跑一套角色"**。

**三类冲突，其中一类 Git 解决不了**：

| # | 冲突 | 严重度 | 能否用 Git 解决 |
|---|---|---|---|
| ① | **角色身份冲突**：两个副本里各有一个叫 `developer` 的角色，**记忆与台账各自独立**——"它说过什么"会有两个答案 | **最严重** | **不能** |
| ② | **只追加文件的文本冲突**：`code_archive/INDEX.md`、各角色 `MEMORY-INDEX`/`CONSOLIDATION-LOG`/`WORKLOG`、`outbox/`——两端同时追加必冲突 | 中 | 能（但每次都要人工解） |
| ③ | **单文件台账冲突**：`PROJECT-BOARD.md` 是单表，两地同改必冲突 | 中 | 能（但很痛） |

**外加**：邮箱是**文件系统内的**，不是网络的——A 的角色发信给 B 的角色，**只有 push/pull 之后才看得到**，且"谁拉取、多久拉一次"没有机制。

**"同时开发不同模块"**：不同模块 → 冲突落在代码文件上，属常规 Git 冲突，**可控**；
同一模块 → 会撞同一文件甚至同一行，**必须靠模块所有权避免**。
**真正危险的**不是代码冲突，而是两个用户各自派活、**同时改同一模块**——那会直接削弱"每任务只有一个主责"这条不变量。

### 三档改造（写入手册 §10）

1. **档 1（推荐先做）**：**产物共享、状态不共享**——只把各角色交付产物、`code_archive/`、手册纳入共享主干；`mailbox/`、`memory/`、`worklog/` 属本地状态，不参与合并。
2. **档 2（要真并行就得做）**：**模块-owner 表 + 分支隔离**；并且**把只追加文件改成"每主体一份"**（`WORKLOG-<user>.md` 等）——合并时是**拼接**而不是抢同一行；**归档只由一人执行**（否则出现两条版本号序列）。
3. **档 3（成本最高）**：**角色集中托管**，把工作流做成服务——当前设计不支持（邮箱与台账都不是可并发访问的介质）。

**动手前请先定三件事（这是人的决定，AI 不能替你定）**：① 模块-owner 表；② 哪些目录进共享主干；③ 归档由谁执行。
