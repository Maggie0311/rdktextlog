## 1. 背景 (Context)
委托层对 framework_admin 提出两个结构性质疑：
① `_framework/` 是我的还是写给别人也看的？让新角色阅读它是否合理？
② 邮件人称逻辑混乱（同一封信里"你"指不同角色），造成"一个人模仿许多人的大脑"。

## 2. 目的 (Objective)
回答这两个问题，并请委托层在两个问题的候选方案中做出选择。

## 3. 请求 / 交付物 (Request & Deliverable)

### 3.1 核查所得（事实）
- `_framework/` 现位于 `framework_admin/_framework/`（**由委托层从根目录移入**——这本身是对我一次越界的纠正）。
- 非我目录内的 `_framework/` 引用 **151 处，分布 4 个角色、57 个文件**；其中**要求对方去读的义务型引用 32 处**。
- 我发出 18 封信：**7 封 `to: all`**、6 封单角色、5 封给委托层。典型问题：一封 `to: all` 通告里，
  "你"在三个小节里分别指 `developer`、`management` 和所有人。

### 3.2 我的回答（`_framework/` 到底想干什么）
`_framework/` **不属于共享规范，属于我的内部档案**，里面混着两类东西：
- **A 类（本属我私有）**：角色注册表、契约模板、裁决档、模板、审计条款与 V 码 → **别人不需要读**；
- **B 类（对他人有约束力的通用规则）**：邮箱字段与消息语义、记忆模型、命名与不可变性、提交隔离、审查门、角色自足原则
  → **别人必须满足，但不必须通过读我的目录来满足**。

**我的错误不在 B 类规则的存在，而在 B 类的载体**：我用"**引用**"（"见 `_framework/xx`"）代替了"**签发**"
（把规则逐条实例化后写进对方自己的契约）。后果：① **契约不自足**（与其自身义务的一半散落在别人家里，与 `§2.1` 自相矛盾）；
② 把我私人档案的结构强加给对方；③ 边界模糊——角色的记忆里出现"来自 `_framework/` 根规范"，使它的义务看起来像"外来的规矩"。

**需要纠正一处可能的误解**：不是"通用规则别人不该知道"——通用规则**必须**对他们有效；
问题只是**载体**：应由我**签发进他们的契约**，而不是让他们来我的目录自学。

### 3.3 请委托层选择（问题一）

| 方案 | 内容 | 代价 | 风险 |
|---|---|---|---|
| **甲** | 私有化 + 内联化：`_framework/` 定性为我的内部档案；32 处义务型引用**裁剪后完整内联**进各角色契约；引用只作溯源注释 | 一次性改写 32 处 | 改写期间双份表述可能漂移 |
| **乙** | 抽出一本"公共规则手册" | —— | **基本不可行**：无公共工作空间时，它只能放进某角色家里（回到问题）或另建共享区（违反 §2.1） |
| **丙** | 只改"要求阅读"，不做内联 | 最低 | 规范漂移：同一规则长期存在两份表述 |
| **丁（我建议）** | **甲 + 制度化**：在 `§2.1` 增补"**任何角色的行为义务必须能在其自身目录内闭合**"，并加入建角色检查清单与审计项 | 多一步制度设计 | 需防止被误解为"禁止只读他方" |

### 3.4 请委托层选择（问题二）

| 方案 | 内容 |
|---|---|
| **甲** | **人称与收件人硬规则**：`你` 只能指收件人，第三方一律写角色代号；一封信只承担**一条边**（`TASK`/`QUERY`/`RESULT`/`ISSUE`/`HANDOFF` 必须单一收件人）；`to: all` 只允许 `NOTIFY` 且公告中**不得出现"你"**；`cc` 不得携带行动要求 |
| **乙（我建议）** | 甲 + **信/文档分离**：长规范内容不进信正文（改为"你的契约第 X 条"）；信正文只留四件事——**要你做什么 / 何时 / 怎么算完成 / 你要回什么**；并设长度上限 |
| **丙** | 乙 + **处理存量**：对**尚未上岗**的三个角色（`developer`、`code_reviewer`、`software_tester`）的任命信**按新规则重签**（它们尚未读，成本为零）；已读通告保持原样（历史不改写） |

**我的建议**：问题一选 **丁**；问题二选 **乙 + 丙**。
