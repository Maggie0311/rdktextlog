## 观察 (Observation)
创建 R-005 `software_tester` 时发现一个此前**四轮建角色都没遇到过**的问题：
`developer` / `code_reviewer` 的能力是"语言与判断"层面的（写代码、读代码），本框架能直接判断其可行性；
但 `software_tester` 的能力是**物理与工具链层面**的（能否编译、能否烧录到单片机、能否连远程机、能否读串口）——
**这些能力与框架、契约、规范全都无关，只与这台机器和这些设备有关**。

若按前几轮的做法直接给它写"你可以烧录单片机、可以经串口在其它计算机上测试"，那就是**把假设写成了能力**。
一旦实际不可用，它要么交不出东西，要么在压力下编造结果（触发 V8）。

处理方式：随角色一并交付一份 `script/ENVIRONMENTS.md` 骨架，
**每一条都标"假设"**，并把"实测回填"设为上岗首任务（AC1/AC2），
同时登记缺口 **G7**（测试环境可用性未验证）。

## 提炼 (Generalization)
**能力型角色**（其"能不能做"取决于外部条件而非其自身判断的角色）在创建时必须同时交付：
① 一份**能力清单骨架**，每一项显式标注"**已验证 / 假设 / 不可用**"；
② 一个**以实测回填清单为首任务**的任命安排。
**未标注状态的能力条目，在实践中会被读成"已具备"**——这本身就是一种默示承诺，
而它一旦落空，压力会全部转移到该角色身上，最终以伪造结果的形式爆掉（V8）。

## 待验证 (To Verify)
需在**下一次创建能力型角色**时验证（例如未来的"部署发布者""现场调试员""数据采集员"——凡能力取决于设备/网络/权限的角色）。
若"清单骨架 + 实测首任务"这一组合确实避免了虚报 -> 可考虑晋升为长期记忆；
若仍有角色在未实测的情况下对外承诺 -> 说明还缺一条**强制机制**（例如要求其首份 RESULT 必须包含能力清单的实际状态）。

反面待验证：是否会造成过度谨慎——把"清单没写就不敢做"变成拖延的借口。
判断标准应是"**能马上实测的就实测**，而不是"没写就不动"。

## 应用方式 (How to apply)
创建任何**能力取决于外部条件**的角色时：
1. 列出它需要的能力项（工具、设备、连接、权限）；
2. 随角色交付一份**能力清单骨架**，每项标注 **已验证 / 假设 / 不可用**；
3. 把"实测回填 + 一次端到端最小验证"设为**上岗首任务**，并给出可验收的 AC；
4. 在规范或通告中写明：**未标"已验证"的能力一律不得对外承诺**；
5. 登记对应的缺口编号，便于日后审计"承诺是否发生过"。
