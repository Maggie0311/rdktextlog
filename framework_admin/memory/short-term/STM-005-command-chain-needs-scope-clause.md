## 观察 (Observation)
本轮首次在框架中引入**真实指挥链**：用户要求 R-003 `developer` 既"与 R-001 平行同级"，又"听从 R-002 统领"。
这两个要求在字面上看似矛盾，实际是两个不同的问题被混在了一起：
- "同级"回答的是**治理关系**（谁定义边界、谁仲裁）；
- "服从"回答的是**执行关系**（谁分派任务、谁验收）。

真正需要裁定的不是"谁大"，而是**服从的边界落在哪**。裁定为 **WHAT/WHEN 服从、HOW 自主** 后，
"写什么"（M1/M3）与"怎么写"（D1/权力轴）被判定为**两个不同的问题而非同一动作**，冲突面随即消解。

## 提炼 (Generalization)
当新增角色对既有角色存在（或部分存在）服从关系时，契约里**必须**有一节显式写明"服从什么、不服从什么"，
且两侧都必须**可判定**（能举出属于/不属于的例子）。只写"听从 X 的统领"是不合格边界：
它无法回答"X 能否指定实现方式"这一必然被问到的问题。

## 待验证 (To Verify)
**2026-09-23（第 2 次）：跨任务复现成立，置信度 0.35 -> 0.45。** 第二次场景是**校验型角色**（`code_reviewer`），
其服从关系比 `developer` 更微妙：服从"审什么、何时审"，但**不服从"审出什么结论"**。
"WHAT/WHEN vs HOW"这一对轴无法直接覆盖它——本轮实际使用的是**扩展形式**：
**PROCESS（流程：审什么/何时审 —— 服从） vs VERDICT（结论：审出什么 —— 不服从）**。

因此本经验的表述应修正为：**服从范围必须按"角色产出物的性质"来切**——
产出"交付物"的角色，切在 WHAT/WHEN 与 HOW 之间；产出"判断"的角色，切在 PROCESS 与 VERDICT 之间。
（见新增的 `STM-006`。）

仍需验证：① 出现**第三种**产出性质（例如"裁定/仲裁"型）时，是否还能找到对应的切分轴；
② 反面——服从范围写得太细是否导致协作僵化。晋升还差：`evidence_count` 需 ≥3（现 2）+ ≥1 次独立确认。

反面待验证：是否存在"服从范围写得过细"导致协作僵化（每次都要引条款）的情况。

## 应用方式 (How to apply)
创建任何存在服从关系的角色时：
1. 先分开"治理关系"与"执行关系"两个问题，不要合并回答"谁大"；
2. 为服从关系写出**可判定**的范围（至少覆盖"做什么 / 何时交 / 怎么做"三类）；
3. 明确"不服从"的部分及其维权路径（发 ISSUE 要书面裁定）；
4. 用一句自守句固化，例如本角色的：**"甲方的要求我服从，实现的路我自己走；验收的话我说了不算。"**
