## 观察 (Observation)
2026-09-23 创建 `developer` 时，我在**角色目录之外**设立了 `src/` 作为"项目交付产物区"，
并为此写了整套跨角色写入者规则（`05-CONVENTIONS v1.1 §7.1`）。

2026-09-24 委托层（人类用户）指出：代码写在角色自己的 `script/` 里就够了——这既符合"每个角色一个文件夹"的定义，
也符合框架对 `script/` 的原始定义。核查结果：`src/` **从未被创建**（零迁移），全仓 **40 处**引用需要清理。

**责任在我，且这不是口味差异，是自相矛盾**：
- `00-ARCHITECTURE §2/§3` 早已定义 `script/` = "我**产出**了什么可用东西 / 可复现的资产"；代码正是可复现资产；
- 我却引入第三种区域类型，把一个**角色内部**的问题（交付物放哪）上升成需要根规范约束的**跨角色**问题
  （违反 P6 最小充分、P10 规范性递减）。

## 提炼 (Generalization)
本框架的目录模型是**角色自足**的：一个角色一个文件夹，产物落在自己的 `script/`，跨角色流转靠邮箱。
**新增任何顶层共享目录之前，必须先问"现有角色的目录定义是否已经覆盖了它"。**
若已覆盖，新增即为重复建设，且必然附带额外的跨角色规则负担——而规则越多，越容易自相矛盾。

它现在是**规则**，不再是候选经验。其表述也已从"**先检查是否已被覆盖**"强化为"**一律不得设立**"。

## 待验证 (To Verify)
下次（包括我自己）提出"新增一个顶层共享目录 / 区域"时，验证这套三问是否真的阻止了重复建设。

**反例条件**：若届时确实存在**外部强制**的目录要求（例如某工具链硬性要求特定源码根目录，
且无法通过配置或软链接解决），则本经验需补充"何种证据才足以支持新增共享区"——
即"真实损失"必须来自外部约束，而不是来自预想。

## 应用方式 (How to apply)
收到"新增顶层目录 / 共享区"的提案时，按顺序问三问：
1. **现有角色的哪个目录已经承担了这件事？**（先查 `00-ARCHITECTURE §2/§3` 的七目录定义）
2. **如果放进角色目录，会有什么真实损失？**（不是"不方便"，而是"做不到"）
3. **这个损失能否用邮箱流转解决？**（打包 + 路径 + commit hash + 可复现命令）

三问都指向"必须新建"时，才提交 DECISION；否则一律并入现有角色目录。
