## 观察 (Observation)
创建 R-002 `management`（用户要求"与 framework_admin 平行同级、统领项目全局"）时，初看有 6 个动作可能同时落在两个角色的"只能做"里：
派活、定验收标准、查交付是否合格、对接人类用户、建角色、判定角色失能。

按"谁级别更高"或"谁管得更宽"去切，6 项全部会陷入拉锯（因为"同级"本身不含任何排序信息）。
改用**层**切分后（元层=谁能做什么 / 执行层=这次谁做什么），6 项在几分钟内全部得到唯一主责裁定，
且每项都能给出可判定的边界（如"契约层 DoD 归 admin、任务层 AC 归 management"）。

## 提炼 (Generalization)
当新增角色与既有角色职责相邻时，**先找切分轴，再写契约**；切分轴应选"变化频率不同的两个层"，
而不是"权限大小"或"管辖范围"。按层切分产出的边界可判定；按级别切分产出的边界必然重叠。

## 待验证 (To Verify)
**2026-09-23（第 2 次）：跨任务复现成立，置信度 0.35 -> 0.45。** 但本轮同时暴露了该方法的**适用前提**：
当两个角色之间存在**指挥关系**（R-002 → R-003）时，仅分"治理层 / 执行层"不足以保证边界可判定，
必须把层再细分为 **WHAT/WHEN（服从）与 HOW（自主）** 才能消解"写什么 vs 怎么写"这一对动作
（见 `DECISION-20260923-003 §3` 与新增的 `STM-005`）。

仍需验证：① 若将来出现无法归层的动作（例如"谁来定义接口契约"这类横跨两层的动作）-> 本经验需扩展到三段式切分；
② 其反面——是否存在"层切分过度"：把本可合并的职责切成两层，反而增加通信成本（P6 最小充分）。

晋升还差：`evidence_count` 需 ≥3（现 2）+ ≥1 次独立确认。

## 应用方式 (How to apply)
创建任何与既有角色职责相邻的角色时：
1. 先枚举"可能同时被两边认领"的动作（不写契约）；
2. 对每个动作问"它回答的是'谁能做'还是'这次谁做'"；
3. 归层后指定唯一主责，写进裁定表；
4. 裁定表完成后才动笔写 ROLE-LIMIT。
