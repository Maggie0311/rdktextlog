## 观察 (Observation)
创建 R-006 `maintainer` 时遇到一类此前没处理过的角色：它**不产出物件，也不产出判断**，
而是产出**人类理解代码的认知基础**（说明书 / 补注 / 答疑），人类将据此**长期维护**与**最终裁决验收**。

这类角色的失效模式与前三类完全不同：
- 生产型角色（`developer`）的失效是"**做错了**" → 用审查与测试兜住；
- 判断型角色（`code_reviewer`）的失效是"**判错了**" → 用申诉与证据门槛兜住；
- 运行型角色（`software_tester`）的失效是"**报错了事实**" → 用原始输出与覆盖声明兜住；
- **认知型角色（`maintainer`）的失效是"给出一个错误但看起来很合理的解释"**——
  它**不会报错**，不会被任何现有机制拦住，而人类会**据此维护代码、做出裁决**。

处理方式：把它的核心风险**写成契约里的结构性要求**，而不是靠"要求它认真"：
① 说明书强制包含 **事实层与推断层的分离声明**（哪些是代码确实这么写、哪些是我推断的意图）；
② 强制包含 **未解疑问（`unverified`）** 一节，并明文写"**必须列出，禁止省略**"；
③ 关键结论必须给 `file:line`；
④ 自守句：**"宁可写'我不确定'，不可写'应该是这样'。"**

## 提炼 (Generalization)
当角色的产出是**他人的认知基础**时，它的质量指标不是"完整、好看、自洽"，
而是"**准确 + 明确标出边界**"。因此它的契约里必须有：
① 一个**强制**的"不确定项"字段（**列出未解问题不是减分项，省略才是失职**）；
② 事实与推断的**分离要求**；
③ 可定位性要求（结论必须能被人自己核实）。
只写"要准确"是无效要求——**因为它无法被检查**；而"未解疑问必须列出"是可以被检查的。

## 待验证 (To Verify)
需在**首个真实说明书交付后**验证：人类用户能否仅凭 `SPEC` 理解代码结构（委托层的原始要求），
以及"未解疑问"一节是否真的被用上（例如人类据此提问、或据此发现 maintainer 的理解偏差）。
若人类仍被误导 -> 说明光有字段不够，需要更强的机制（例如**强制人类确认**：说明书须经用户过一遍才算完成）。

反面待验证：**过度自谦**——每一条都标 `unverified` 会让说明书失去价值。判据应是"我自己核实过没有"，
而不是"我怕说错"。若出现过度标注，需补充"何时可以不标"的判定标准。

## 应用方式 (How to apply)
设计任何**产出认知**的角色（说明书 / 报告 / 解释 / 教学 / 答疑类）时：
1. 先问："它错了会怎样？谁能发现？"——若答案是"没人能发现、但人会据此行动"，则它属于本类；
2. 在契约里加一个**强制的"未解疑问 / 不确定项"字段**，并明文写"禁止省略"；
3. 加**事实与推断分离**要求，以及**可定位**要求（给出位置，让人能自己核实）；
4. 给一句可执行的自守句，例如"宁可写我不确定，不可写应该是这样"。

> 顺带适用：本方法对 `code_reviewer`（发现项五要素）与 `software_tester`（覆盖声明、事实/归因分离）
> 是同构的——只是它们已经各自用了，而**本轮第一次把它明确成"认知型角色"的通用设计方法**。
