## 1. 目标 (Objective)
创建 R-004 `code_reviewer`（代码审查员）：独立检查 `developer` 的代码，按清单与标准查找逻辑错误与缺陷；
建立 `code_reviewer/standard/` 标准区（含**用户自定义标准接口**）；把审查设为 developer 每轮交付的**强制门**。

可验收判据：① 该角色既能"抓住问题"又不会"制造问题"（不误报、不瞒报、不过度要求、不懒惰批准）；
② 人类用户可零门槛地向 `standard/user/` 添加自己的检查点，且该检查点**必然被使用**；
③ developer 每完成一轮工作都被实际拦在审查门之前，无法绕过。

## 2. 约束 (Constraints)
- 本角色硬边界：只做角色定义 / 边界 / 规范 / 任命（A1、A2、A6），**不代做业务产出**（N1），**不替角色做技术判断**（N7）。
- 用户口述硬需求：审查要"确实做到且做好"；**不误报、不瞒报、不过度要求本不存在的错误与返工、不懒惰直接批准**；
  `standard/` 与 memory / mailbox **同级**；留出用户自定义标准接口；建好后向 developer 与 management 介绍；
  以后 developer 每完整工作一次即须调用本角色。
- 已生效的约束：`DECISION-20260923-003 §7` 声明 `developer/` 对 framework_admin 只读；`DECISION-002 §6` 同样约束 `management/`。
  → **本轮不得修改 developer 与 management 的契约文本**，门必须立在**根规范层**（P10：跨角色规则归根层）。
- 命名与不可变性约定（`05-CONVENTIONS v1.1`）。

## 4. 专业方法 (Method)
1. **把"不懒惰批准"与"不误报/不过度要求"这两类相反的失效，落成同一套可判定机制**——
   前者靠 **PASS 的三个必要条件**（覆盖声明 + 验证证据 + 零阻断项），后者靠 **发现项五要素 + 级别门槛**。
   两套机制共用"证据"这一个支点，因此不矛盾。
2. **用户自定义标准的优先级置于最高**，并要求审查报告**逐次列出所应用的用户标准清单**（含"无"的情形），
   使"接口存在"与"接口被使用"成为可审计的两件事。
3. **门立在根规范**（`00-ARCHITECTURE.md §4.1` + 违规码 V7），因为它是跨角色规则，且我无权改他方契约（见 §2 约束）。
