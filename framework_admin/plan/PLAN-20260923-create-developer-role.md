## 1. 目标 (Objective)
创建 R-003 `developer`（开发工程师）：与 R-001 **平行同级**、在项目执行中**服从 R-002 management 的任务编排**，
职责为编写软件代码（C / Python 为主），要求结构清晰、便于维护、风格规范、**详细中文注释**。

可验收判据：给定 `developer/` 与 `_framework/`，一个零上下文执行者能据此独立接活写码且不越界。

## 2. 约束 (Constraints)
- 来自本角色 role-limit 的硬边界：只做角色定义/边界/规范/任命（A1、A2、A6），**不代做业务产出**（N1）；
  **不定技术细节**（N7：代码风格、算法选型属 developer 的专业判断）。
- 来自用户口述的硬需求：与 R-001 平行同级；听从 R-002 统领；代码结构清晰、便于维护、精准完成分派任务；
  风格规范；**详细中文注释**；精通 C、Python 及其他语言。
- 来自 R-002 已生效契约的约束：任务以唯一 `task_id` 下发（M3）；验收权在 management（M7）。
- 来自 `_framework/05-CONVENTIONS.md` 的命名与不可变性约定。

## 4. 专业方法 (Method)
沿用 R-002 已验证的方法：**先枚举冲突面 → 逐项裁定唯一主责 → 再写契约**（STM-004 的验证）。

本轮新增两个必须处理的**结构性问题**（否则新角色无法工作）：
1. **第一条真实指挥链**：R-002 → R-003。此前框架内"同级"等于"无指挥链"，本轮必须显式定义**服从范围**。
   裁定：**WHAT/WHEN 服从（做什么、何时交），HOW 自主（怎么写）**——理由：management 无技术专业身份（其 MN2 已禁止其做业务判断），
   若允许其指定实现细节，等于让无专业判断权的一方做专业决策。
2. **三角色共写一个 git 仓库的踩踏风险**。证据（本轮之前已实际发生）：framework_admin 在 #15、上一轮提交中连续使用 `git add -A`，
   此时若他方存在未提交改动，会被一并卷入提交。故升级根约定 `05-CONVENTIONS.md` 至 v1.1，新增 §7 共享仓库与产物区约定。
